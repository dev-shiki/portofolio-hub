Case Study 01: Universal Workflow Engine

Application-layer AES-256-GCM PII encryption + HMAC-SHA256 blind indexing + append-only audit log. Domain-agnostic state machine handles procurement, HR, maintenance, capex — same engine, different payloads. 

// User: PII encrypted at application layer before DB write
model User {
  // 🔒 AES-256-GCM ciphertext — plaintext never stored
  emailCiphertext  String  @map("email")
  // 🔎 HMAC-SHA256 — enables WHERE email_bidx = ? without decryption
  emailBlindIndex  String  @unique @map("email_bidx")
}

// Generic BPE request — any approval domain
model WorkflowRequest {
  domain        String         // "procurement" | "hr" | "maintenance"
  payload       Json           // typed domain-specific fields
  currentStatus WorkflowStatus @default(draft)

  @@index([domain])
  @@index([currentStatus])
}

// Append-only step log — INSERT only, never UPDATE or DELETE
model ApprovalHistory {
  previousStatus WorkflowStatus
  newStatus      WorkflowStatus
  executedAt     DateTime @default(now())

  @@index([requestId])
}

Case Study 02: Immutable Ledger Trigger

PL/pgSQL trigger enforcing append-only semantics at the PostgreSQL engine level. Cannot be bypassed by application code, API keys, or direct DB sessions — only a superuser DROP TRIGGER (itself a logged DDL event) can remove it. 

CREATE OR REPLACE FUNCTION enforce_ledger_immutability()
RETURNS TRIGGER AS $$
BEGIN
    IF TG_OP = 'UPDATE' THEN
        RAISE EXCEPTION
            'SECURITY VIOLATION: Ledger entry % cannot be modified. '
            'Attempted by session user "%".',
            OLD.id, session_user
            USING ERRCODE = 'restrict_violation';  -- SQLSTATE 23001

    ELSIF TG_OP = 'DELETE' THEN
        RAISE EXCEPTION
            'SECURITY VIOLATION: Ledger entry % cannot be deleted. '
            'Attempted by session user "%".',
            OLD.id, session_user
            USING ERRCODE = 'restrict_violation';
    END IF;

    RETURN NULL; -- cancels the operation
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

-- Attach: fires BEFORE every row-level UPDATE or DELETE
CREATE TRIGGER trg_ledger_immutability
    BEFORE UPDATE OR DELETE ON event_wallet_ledger
    FOR EACH ROW EXECUTE FUNCTION enforce_ledger_immutability();

ADR 0001: 10-Domain Bounded Context Map

Status: Accepted · 2026-06-18

Context

The system spans multiple products (commerce, POS, CRM, AI, invoicing). Without explicit boundaries, everything collapses into one super-app or fragments into ad-hoc tables with no owner. Options evaluated: ~6 broad domains (too coarse — Commerce, Operations, Relationship conflate), ~20 fine domains (too much ownership and CI overhead), 10 domains (optimal balance).

Decision

Adopt 10 domains: Platform · Commerce · Relationship · Operations · Content · Intelligence · Automation · Analytics · Finance · Integration. Each domain owns its model, data, rules, API, events, permissions, and lifecycle. The set is closed — adding or removing a domain requires a new ADR.

Consequences

Every business record has a clear home. Cross-domain collaboration must go through events/APIs, never shared tables. Platform remains a trust layer, not a super-monolith.

ADR 0006: Event Delivery via Transactional Outbox / Inbox

Status: Accepted · 2026-06-18

Context

Domains must collaborate through events, never shared tables. A single paid-order event fans out to seven domains. Three options: in-process emit (loses events on crash — unacceptable for money-adjacent events), message broker now (justified overhead at current scale), or transactional outbox/inbox on the existing DB.

Decision

Adopt the transactional outbox + inbox pattern. The outbox row is written in the same DB transaction as the state change. Each consuming domain owns its own inbox, keyed by event ID — making consumption idempotent (exactly-once in effect) over at-least-once delivery. A real broker can be introduced later between the relay and the inbox without rewriting outbox or inbox tables.

Consequences

No event is lost on crash. No event is processed twice. No new infrastructure required. Every domain pays a uniform, small cost: two tables + relay + dedupe.

ADR 0007: Platform Owns Module Entitlements

Status: Accepted · 2026-06-18

Context

Each product module needs to check whether a tenant has purchased and activated a given feature. If each module implements its own entitlement check, the logic diverges over time, edge cases are handled inconsistently, and a billing change requires coordinating updates across all modules.

Decision

Platform is the single source of truth for module entitlements. Any module that needs to gate a feature calls the Platform entitlement service (or reads from a Platform-owned cache), never maintains its own entitlement state.

Consequences

Billing changes propagate to all modules automatically. Entitlement logic is tested once, in one place. Modules become simpler — they make a single query, not a policy decision. Platform becomes a critical dependency, so its availability SLA matters.

Research: AI Test Generation & Specification Bias

Type: Undergraduate Thesis · Empirical Study

Research Question

Do LLM-generated test suites systematically overfit to the happy path described in a specification, while consistently failing to cover edge cases and negative test paths?

Methodology

Empirical study: LLM prompting with varied temperature & prompt structures → coverage analysis against human-authored test suites → reproducibility testing across multiple sessions.

Key Findings

  • Happy-path bias is consistent and measurable across all tested configurations.
  • Explicit prompting for failure cases improved edge-case coverage significantly, but still below human-authored suites.
  • Deterministic sampling (temperature=0) produces reproducible bias — the same gaps appear every run.
  • Specification quality was the dominant variable — ambiguous specs produced the worst AI coverage regardless of model.

Practical Implication

AI test generation is most effective as a first-pass tool. The bottleneck is specification clarity, not model capability. Structured specs (Gherkin, OpenAPI) improve AI test quality more than prompt engineering alone.
